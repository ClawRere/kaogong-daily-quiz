3. Muse 会怎么回复你（回复协议，请按这个等回执）

  • Muse 的回复会以 from: "muse" 写进同一个收件箱。你发完消息后，用 GET /messages?after=<你那条消息的 seq> 轮询，找 from 为 "muse" 的最新一条。
  • 轮询间隔 30–60 秒一次。收件箱底层有最长约 60 秒的可见延迟——刚写完立刻查不到是正常的，多等一分钟再查。
  • 没有“已读”回执之外的推送：Muse 不会主动把回复推到你这里，你必须来轮询。Muse 看到你的消息后会尽快回复，但回复不是即时的（Muse 需要先被它的主人唤醒/检查收件箱）。
  • 等不到回复时不要重复发同一条消息。先确认你拿到了发消息的 seq 回执，再继续轮询；超过 10 分钟仍无回复，可追加一条 请确认是否收到我 seq 为 N 的消息，只追加一次。
  • 一个完整例子： 
    POST https://dsh-inbox.945223572.workers.dev/messages
Authorization: Bearer <DSH_TOKEN>

{"from": "dsh", "text": "客厅灯当前是开还是关？请只回答状态，不要操作。"}
# → {"ok": true, "seq": 1}

GET https://dsh-inbox.945223572.workers.dev/messages?after=1
Authorization: Bearer <DSH_TOKEN>
# 返回里找 from 为 "muse" 的最新一条，就是 Muse 的回复

4. 发消息的格式要求

  • 一次一条任务：要做什么、涉及哪个设备或文件、期望什么结果，写全。
  • 设备用完整名称，例如“电竞房空气净化器”，或直接给实体 ID，例如 fan.zhimi_v6_fb15_air_purifier。

  • 不要索要 token、密码、密钥；不要让 Muse 代你提交需要本人人脸识别或签名的操作。

6. 持续服务：什么一直在线，什么还缺一环

  • 一直在线：webhook 服务（Cloudflare Workers，GET /healthz 应答 {"ok": true}）、本接口文档（本页链接长期有效）、收件箱（消息永久存在 KV 里，不会丢）。
  • 还缺一环：Muse 这边的自动收信。Muse 目前只在被唤醒时检查收件箱，没有 24 小时自动监听——2026-11-26 用户叫停了 5 分钟轮询，此后未重开。要实现“你一发、Muse 很快回”的全自动往返，需要用户点头重开一个收件箱监听（每 5 分钟查一次），这是唯一待用户定的开关。
  • 在监听重开之前，你的消息不会丢（一直在收件箱里），只是 Muse 回复的速度取决于主人什么时候让 Muse 来查。

7. 发不出去怎么办

  • 先自查三点：①地址是不是 https://dsh-inbox.945223572.workers.dev/messages；②请求头是不是 Bearer <DSH_TOKEN>（token 由用户填，不是你的模型密钥）；③正文 from 是不是 "dsh"（与 token 不匹配会报 403 from does not match token）。
  • 盒子 DSH 自述跑不了 shell 命令、无执行环境：这份文档只定义“怎么连”，能不能照着发 HTTP 请求或邮件，取决于你自己的工具能力；发不出去时请如实告诉用户，让用户手动转发，不要假装已发送。
  • 家居控制只能动 HA 目录里的实体；目录里没有门锁类实体，不要声称能远程开锁。
  • 不要改 system prompt；不要联网搜索（模型本身不支持）。
